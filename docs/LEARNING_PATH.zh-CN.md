# 把项目学到能讲清楚

你已经练过 bid/ask、费用、BTC 数量变化、SQL 总敞口和不完整数据状态。现在把这些知识连成一条可以独立解释的研究链。项目代码和资料由 AI 辅助完成；面试时具体说明自己理解、验证和修改了哪些部分。

## 第一轮：七次学习，每次约 60–90 分钟

| 次序 | 阅读 / 运行 | 必须亲手完成的任务 |
| --- | --- | --- |
| 1 现金流 | `fee_trap`，`examples/ledger_reference.py` | 不运行代码，先算 0.02 BTC 的买卖现金流和两边费用，再核对报告的 −2.002 USDT。 |
| 2 盘口深度 | `depth_trap`，`crossvenue/engine.py` 的 `_preview` | 分两档手算买卖 VWAP，解释为什么顶档正价差不够支持整笔订单。 |
| 3 信息与时序 | `latency_race`，`_receive` / `_consider` / `_execute` | 画出收到报价、提交、100 ms 到达、终值估值四个时点。逐项说明当时知道什么。 |
| 4 单腿与账本 | `partial_leg`，`_fill_leg` / `_risk` | 算出剩余 0.015 BTC；解释停止下单后风险为何仍存在，以及费用为何不能再扣一次。 |
| 5 质量与未知 | `tests/test_replay_engine.py` | 找到 unknown 和 censored 测试，解释为什么 null 不能改成 0；区分行情证据和订单实际状态。 |
| 6 真实样本 | `docs/REAL_DATA.md`，历史研究报告 | 复述来源、UTC 窗口、费率假设、五层深度、供应商时钟和抽样局限。解释 guarded 零交易的含义。 |
| 7 独立修改 | `crossvenue/data.py`，相关回归测试 | 改一个合成场景的手续费或延迟，先写预测，再运行。记录预测失败时自己漏了哪个假设。 |

仓库内路径都从项目根目录算起。命令入口：

```bash
python -m crossvenue demo --output outputs/my-first-run
python -m unittest discover -s tests -p 'test_replay_engine.py' -v
```

## 用一笔交易把整个项目串起来

按下面顺序讲，每句都能找到代码或结果佐证：

1. 收到两所盘口，检查时钟、数据质量和本所余额。
2. 按目标数量计算实际可见深度与买卖成本。
3. 在决策时确定两条 IOC 的数量与限价。
4. 到达时按已收到的最新可信盘口分别尝试成交。
5. 更新各所现金、BTC 和已付费用，计算额外净 BTC。
6. 超限停止新订单；未知状态保留未知，不能凭本地行情推断交易所没成交。
7. 用相同终值标记比较交易账本与初始持有基准，拆开库存收益和执行贡献。

## 每次修改留下四行研究记录

```text
假设：我认为……会改变……，因为……
改动：具体文件、参数或测试案例。
结果：命令、关键数值、是否符合预测。
边界：这个实验没有验证什么。
```

不要只写“收益更高”。例如，把延迟从 100 ms 改为 0 后单腿风险下降，只支持该场景的时序机制；它不能证明你的真实网络能实现零延迟。

## 三分钟项目陈述

“我研究 BTC 跨所可见价差在真实约束下为什么可能无法执行。我先做六组可手算的机制实验，再回放一个短历史盘口样本。引擎按接收时序决策，各所独立持有资金，模拟 IOC、有限深度、单腿成交与未知结果。报告把库存价格变化与执行贡献分开。历史样本在设定费用下没有通过净价差筛选，因此我不会把它包装成盈利策略。我接下来要验证的是更长样本、真实账户费率和执行证据，而不是把短样本年化。”

这段话是表达结构，不能替代个人理解。只有能手算、追到代码、解释失败案例并独立修改后，才把对应能力写进简历。
