# 第四节用 SQL 核对账户敞口

目标：将持仓明细汇总为每个账户的净额和总名义敞口，再理解聚合后限额筛选。只使用 SQLite 内存中的合成数据。

## 数据口径

表名 `positions`。所有行来自同一标的、同一快照，每行代表一个独立头寸；`position_id` 唯一。正值表示多头、负值表示空头，金额已经换算成 USDT。

| account_id | position_id | signed_notional_usdt |
| --- | --- | ---: |
| A | 1 | 800 |
| A | 2 | -700 |
| B | 3 | 600 |
| B | 4 | -200 |

该表用于练习独立多空头寸的风险聚合，与原 long-only 现货模拟分开，不表示现货引擎已经支持开空。

## 第三步选择完整历史快照

如果明细表按分钟追加全量快照，同一头寸在不同时点的状态不能直接相加。需要保留所选快照中的全部持仓明细，再做账户聚合；每账户只保留一条明细会漏掉其余头寸。

`day04_snapshots.py` 提供下一组独立合成数据，表结构为：

```text
snapshots(snapshot_id, snapshot_time, is_complete)
positions(snapshot_id, account_id, position_id, signed_notional_usdt)
```

时间均为北京时间且格式一致。`snapshot_id` 只是标识，不代表时间先后。明细粒度为每个快照、账户、独立头寸一行，复合键为 `(snapshot_id, account_id, position_id)`，每笔金额已统一成 USDT。

| snapshot_id | snapshot_time | is_complete |
| ---: | --- | ---: |
| 101 | 2026-11-08 10:00:00 | 1 |
| 99 | 2026-11-08 10:01:00 | 1 |
| 205 | 2026-11-08 10:02:00 | 0 |

本题约定：标为完整的快照覆盖该时点 A/B 全部当前独立头寸，全部属于同一标的。`is_complete=0` 表示采集尚未完成。完整性是明确给定的教学条件，真实数据需要通过采集流程与覆盖范围核验，不能仅凭行数相等判断。

第一问：先从 `snapshots` 表选择按时间最新的完整快照 ID，写出 SQL。暂不聚合 `positions`。

查看合成快照元数据：

```bash
python3 exercises/day04_snapshots.py
```

学习者已提交按完整性过滤、按时间倒序取一条的查询，保存为 `day04_latest_snapshot.sql`。它选出 99，排除了时间更新但未完成的 205，也没有错误地按编号最大值选取。

```bash
python3 exercises/day04_snapshots.py --sql exercises/day04_latest_snapshot.sql
```

接下来把快照选择与明细聚合连接：在 `positions` 中仅保留该快照的全部持仓，再按账户计算 `net_usdt` 与 `gross_usdt`。使用子查询或 CTE 复用选择逻辑，避免把 99 写死。

首次组合尝试只是串接两条独立 SELECT，尚未建立筛选关系。助手已将组合写法示范在 `day04_latest_exposure.sql`：用外层 `WHERE snapshot_id = (...)` 将内层选择结果用于过滤持仓，再做账户聚合。子查询内不写结束分号，整个语句在末尾结束；使用英文括号。

学习者已说明：若快照99中A有三条头寸，WHERE之后保留三条，GROUP BY后A输出一行。随后参照组合结构补充 HAVING，查询保存为 `day04_latest_breaches.sql`，助手只规范排版及末尾分号。

```bash

```

查询返回0行：完整历史快照99的A/B总额均未超过1,000。请解释：这是否足以证明10:02当前也没有超限？结合快照205尚未完整的事实回答，区分已知未超限与当前数据不足。

快照 205 未完成，选出较早的完整快照只能回答其历史时点的账面状态，不能据此宣布当前风险安全或自动恢复交易。

## 第四步检查完整性与时效

完整历史快照没有查到超限，只描述那个历史时点。若更新快照尚未完整，不能仅凭旧查询0行确认新时点未超限；已经独立核实的风险事实仍需保留。独立合成题设中，判断时刻10:05、最新完整数据10:01，数据年龄为240秒；本题允许最多60秒，因此不满足时效要求。

`day04_data_quality.py` 中的 `data_usable` 只检查两项条件：完整，以及数据年龄处于 `[0, max_age_seconds]`。本题假设输入已标准化且时钟统一；负年龄视为时间异常。返回True仅表示该快照满足这两项条件，不判断敞口、数据其他质量或是否可以恢复交易。

学习者初稿用 `and` 连接条件，助手修正了 `=` 的使用、反引号和不包含端点的比较；因此该函数为指导下修正版本，不能记作初稿已完全正确。

```bash
python3 exercises/day04_data_quality.py
```

演示的60秒是本课给定阈值，由调用者传入。不同业务应使用其明确规定的时效规则。

## 第五步完整性标记的来源

练习中的 `is_complete` 是采集系统依据约定维护的批次元数据。实际采集应先明确需要覆盖的交易所、账户、产品和方向范围，再核对哪些必需请求及分页已完成；未解决的失败、遗漏页面或未提交的数据不能当作已完成。

可检查以下证据：

| 检查 | 需要核对的证据 |
| --- | --- |
| 应采集范围 | 预先配置的必需范围与本批成功范围逐项匹配，不能只比较数量 |
| 请求与分页 | 请求业务结果、每页游标及最后一页已读完；失败重试的最终结果明确 |
| 明细与空仓 | 关键字段齐全、头寸键有效且无重复；明确零仓和请求失败/缺数据的区别 |
| 批次发布 | 同批次先暂存、校验并提交，全部完成后发布完成标记；保存开始结束时间与错误原因 |

Bybit 持仓接口提供分页游标 `nextPageCursor`，还区分产品与持仓方向；部分查询只返回非零持仓，因此行数减少也可能来自平仓。参见[官方持仓文档](https://bybit-exchange.github.io/docs/v5/position)。

全量快照与增量推送应按接口语义处理。比如 Binance 现货 `outboundAccountPosition` 包含可能发生变化的资产，不能把每条消息当成完整账户资产清单；参见[官方用户数据流文档](https://github.com/binance/binance-spot-api-docs/blob/master/user-data-stream.md)。增量方式需要已有基线并处理断线后的同步与对账，不凭收到一条推送就判断收齐。

以上是工程检查思路，不是本项目已实现的交易所采集器。翻完分页也不保证来自同一瞬间，需要另核对采集窗口及期间变动；范围完整、时点一致和数据足够新分别验证。若只有明细表而没有采集完成证据，应保留完整性未验证的状态。

## 第六步不完整与已知风险同时存在

数据不完整不能用于证明未超限；但在已收到明细均正确、属于同一时点及限额范围、单位一致且无重复的前提下，总名义敞口是非负绝对值之和。若已知部分已达1,500、限额1,000，则该时点总额至少1,500，已经确认超限，精确总额仍未知。

这一下界结论不适用于可能被相反头寸抵消的带方向净额。`data_usable=False` 不能用来抹去已独立核实的风险事实，也不能自动推断当前时点与历史时点相同。
