# 第三节读懂均线信号和信息时序

目标：解释现有模拟项目怎样产生信号，以及决策时已经知道哪些数据。先读代码和手算，再讨论历史成交假设。

在现有 `crypto-paper-lab` 项目的 `cryptopaper/engine.py` 中，`signal_series` 使用这些核心步骤：

```python
fast = close.rolling(spec.fast, min_periods=spec.fast).mean()
slow = close.rolling(spec.slow, min_periods=spec.slow).mean()
signal = (fast > slow) & slow.notna()
```

`rolling(n).mean()` 表示包含当前行在内、最近 n 个收盘价的平均值。`min_periods=n` 要求已经有 n 个数据点，数据不足时均线为缺失值。`slow.notna()` 检查慢均线是否已经形成。

## 第一步手算信号

三根连续 K 线的最终收盘价依次是 100、101、102。快窗口为 2，慢窗口为 3；快均线大于慢均线时，信号为 True。

1. 第三根结束时，快均线和慢均线分别是多少？信号为 True 还是 False？
2. 第三根刚开盘时，是否已经知道它最终收盘价是 102？能否提前使用据此算出的信号？

## 第二步解释预热期

前三行中哪些行能形成慢均线？数据不足时不产生买入信号，和“市场没有机会”是否是同一个意思？

## 第三步检查下一根执行

在原项目回测代码中找到 `signal_series(frame, spec).shift(1, fill_value=False)`。解释为什么把信号推迟一行。然后将第四根收盘价设置为 90，检查改变它是否应该影响前三根信号。

给定收盘后信号序列 `[False, False, True, False]`，手写向后移动一行、第一行用 False 填充后的序列。解释移动后的 True 来自哪根 K 线的收盘数据。

历史回测按下一根开盘价模拟成交是一项执行假设。实时运行还要等待收盘数据到达、完成计算并发送订单，实际成交价不能保证等于该开盘价。

## 第四步从信号到目标仓位

现有项目把做多信号映射到目标权重，再比较当前持仓与目标，生成调仓数量。目标权重是希望持有的总规模，不是每次信号出现都重新买入同样的总规模。

合成题设：总权益 10,000 USDT，其中现金 6,000、BTC 市值 4,000，目标 BTC 权重为 45%。本题忽略手续费、滑点、点差和价格变化。

计算目标 BTC 市值及当前需要新增买入的金额。接着考虑：第一笔完成、账本已更新后，若价格和目标都不变，再次出现相同信号是否还需买入？

`day03_target.py` 已按学习者提交的方法整理为 `target_gap`，只删除第一行末尾多余的减号并保留两步计算。可在本项目目录执行 `python3 exercises/day03_target.py`，核对当前 BTC 市值分别为 4,000、4,500、5,000 时的理论差额。

在原项目的 `rebalance` 中找到权益、目标持仓数量和调仓差额的计算。目标权重不等于硬风险上限；价格变化、容差和最小成交额可能留下偏差。重复调用纯函数时要传入更新后的状态，这与账本层的重复信号保护是两个问题。

## 第五步区分理论差额与调仓容差

原项目默认只在实际权重与目标权重的绝对偏差至少达到 0.02 时允许调仓，0.02 是 2 个百分点。实际执行同时还有最小成交额、费用和余额等约束。

合成题设：总权益 10,000 USDT，当前 BTC 市值 4,400，目标权重仍为 45%。理论差额为 100 USDT。只考虑上述容差，这次是否会调仓？请说明权重偏差是多少。

## 面试复述

用自己的话说明：信号依赖哪些数据，最早何时可知，何时模拟执行，以及真实执行还缺少哪些条件。原项目使用均线作为工程基线，其盈利能力需要另外研究，不能由信号计算正确直接推出。

本节用 4 至 6 句话复述：均线怎样产生信号、`shift(1)` 怎样避免提前使用收盘信息、怎样按当前持仓与目标的差额调仓，以及为什么目标权重不能直接充当硬风险上限。阅读现有引擎和完成简化计算练习分别描述，不把已有引擎说成此次独立从零实现。
