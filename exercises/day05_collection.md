# 第五节检查采集批次是否可以发布

目标：将完整性检查变成明确的采集步骤和布尔条件。全部使用合成状态，不访问交易所、不采集真实账户。

## 第一步读懂采集状态

本题只监控同一产品下的 A、B、C 三个账户，每个都需要完成所有必需请求和分页。

| 账户 | 本批采集状态 |

## 第三步区分可以发布与已经发布

`ready_to_publish=True` 只表示发布前条件满足。明细与完成标记仍应按设计在同一事务中成功提交，消费者才能将该批作为已发布的完整数据读取。若提交失败，不能把批次标成已完成。

理解题：发布前检查已通过，但事务明确失败且已确认回滚，明细与完成标记均未提交成功。此时能否标为已完整发布？与仅收到提交响应超时、尚未核实实际结果的情况要分别处理，后者不能直接推断提交成功或失败。

学习者已正确区分两种情形：明确回滚不能作为完整发布；提交结果未知时，先回读该批明细和完成标记，再决定是否重试。应按同一批次ID核对权威数据库的已提交状态和整批内容。暂时未查到记录不单独证明已回滚，原事务可能仍未决；查到一条明细也不证明整批完成。

## 第四步用稳定批次ID识别重试

本题将“幂等”理解为：同一批数据重复处理，不额外产生一份重复结果。下面只讨论同一批、同一内容的重试，不是采集新的时间点。

假设独立教学表的组合主键为：

```sql
PRIMARY KEY (snapshot_id, account_id, position_id)
```

表中已经提交一条 `(300, 'A', 1)`，数值为800。分别使用普通 `INSERT` 重试：

| 方案 | 重试写入的主键 | 内容 |
| --- | --- | --- |
| 1 | `(300, 'A', 1)` | 与原记录相同 |
| 2 | `(301, 'A', 1)` | 与原记录相同，仅更换批次ID |

判断：哪个会触发主键重复？哪个会被数据库视为新记录？如果新采集了另一个时间点的数据，使用新批次ID是另一种情形，不与本题的同批重试混淆。

讲解：三列共同构成一个主键，不要求每列单独唯一。只有三列值全部相同时才触发本题的主键重复。因此方案1与已有键相同；方案2的批次ID不同，会被视为新记录。同一批重试若更换批次ID，就无法靠这个主键识别为原批次的重试。进一步判断：已有 `(300, 'A', 1)`，插入 `(300, 'A', 2)` 是否触发这个主键的重复约束？

稳定ID帮助识别重试，主键约束帮助阻止重复键。两者本身不构成完整的幂等发布流程：还需核对同ID内容是否一致，以及整批明细和完成标记是否成功提交。重复键报错不能直接当作成功；同ID但内容不同应明确处理冲突，不能静默忽略或自动覆盖。上述概念题不执行发布，最后一节另用内存参考演示事务与重试。

## 第六步将单条内容判断写成函数

本题只分类，不执行数据库写入。假设已经成功查询同一个组合主键，`existing_value` 是查到的非空整数；仅在成功查询且没有该记录时传入 `None`。查询超时、失败或字段缺失不能当成 `None`，也不能凭暂未查到一条记录认定整批事务已回滚。`incoming_value` 是这次提交的非空整数，0是有效值。

| 条件 | 返回值 | 含义 |
| --- | --- | --- |
| `existing_value is None` | `"new"` | 该主键未查到记录，仅为待插入候选 |
| 已有记录且数值相同 | `"same"` | 仅这一条内容一致 |
| 已有记录且数值不同 | `"conflict"` | 需要核查冲突 |

原编程题要求补充下面骨架中的比较条件：

```python
def record_status(existing_value, incoming_value):
    if existing_value is None:
        return "new"
    if ______:
        return "same"
    return "conflict"
```

不能用 `if not existing_value` 识别不存在，因为已有值0也会被判断为假。`new` 不表示已经写入，`same` 不表示整批已发布；整批成功仍需核对完整记录集和完成标记。

学习者首次写了 `existing_value=incoming_value`。助手修正为比较表达式 `existing_value == incoming_value`：`=` 是赋值，`==` 才是相等比较。对于 `record_status(0, 0)`，学习者最初回答True；助手解释条件 `0 == 0` 得到True，但函数执行 `return "same"`，最终返回字符串。随后学习者正确回答 `record_status(800, 900)` 返回 `"conflict"`，因为两个数不相等。

修正后的完整函数已保存到 `day05_collection.py`，分支骨架和比较符号由助手提供或修正，不记为学习者独立从零实现。运行脚本可查看不存在、相同、冲突和已有零值四种合成演示。

## 第九步复测不完整数据中的风险结论

另设一个尚未采集完的新批次，不是将上面已完整发布的批次改成未完成。已收到A的两个独立头寸，带符号名义金额分别为+800和-700 USDT；已核实二者数值正确、没有重复、属于同一时点和同一限额范围，且估值口径一致。A可能还有其他头寸尚未收到，B/C采集也未结束，因此整批 `is_complete=False`。

本题限额是A的总名义敞口 `SUM(ABS(signed_notional_usdt)) > 1000`，不是净敞口。回答：已核实部分的总名义敞口是多少？能否确认A在这个时点已经超过1000，为什么？不自动将该时点结论外推至当前。

学习者回答“1500，不能，因为数据没全”。计算正确，结论需修正。在上述核实条件下，未知独立头寸的绝对值之和非负，因此：

```text
该时点A总名义敞口 = 1500 + 未收到头寸的绝对值之和
                  >= 1500 > 1000
```

所以可确认该时点A已超限，精确总额仍未知，整批仍未完整。不能以数据不完整为由清除已经由可信下界证明的风险，也不能将此推理直接套用于带符号相加的净敞口。

继续复测：若又收到同一时点A的另一条独立头寸-400 USDT，已核实条件保持不变，已收到三条的总名义敞口是多少？尚未据此认定整个账户已采集完整。

学习者正确回答1900。随后对“已核实部分总名义敞口700、其余未知、限额1000”分别判断是否能确认超限、是否能确认未超限，学习者回答“不能，不能；数据没有齐全”，两项判断正确。700这个下界不足以证明超过1000，未知部分又可能使最终总额超过1000，所以风险结论为unknown。

## 第十步将风险判断写成函数

本题 `observed_gross` 是同一账户限定范围内、同一时点和估值口径、已核实且无重复头寸的绝对金额之和，不是净额，也不混加历史快照。`is_complete` 指该判断范围内的头寸是否已按采集证据确认取齐。金额与限额为有效非负整数USDT，完整性为标准布尔值，输入校验不在本函数实现范围。

按这个顺序判断：

| 条件 | 返回值 |
| --- | --- |
| 已核实部分已经严格超过限额 | `"breach"` |
| 尚未证明超限，而且该范围数据未完整 | `"unknown"` |
| 该范围数据完整，且未超过限额 | `"within_limit"` |

原编程题要求补充第一处条件：

```python
def gross_risk_state(observed_gross, is_complete, limit):
    if ______:
        return "breach"
    if not is_complete:
        return "unknown"
    return "within_limit"
```

先判已确认超限，再判是否完整，避免把已证明的风险降为unknown。限额按严格大于处理；等于1000时，未完整为unknown，已完整才为within_limit。`within_limit` 仅表示该时点该项总名义敞口未超限，不表示数据新鲜、其他风险已排除或可以恢复交易。

学习者首次正确提交 `observed_gross > limit`。助手保留此条件，将完整函数和六种合成演示保存为 `exercises/day05_gross_risk.py`；分支顺序与骨架由助手提供，不记为学习者独立设计整个函数。


运行前先判断：`gross_risk_state(1000, False, 1000)` 和 `gross_risk_state(1000, True, 1000)` 分别返回什么？限额定义仍是严格大于。

学习者正确回答三个调用 `(1500, False, 1000)`、`(1000, False, 1000)`、`(1000, True, 1000)` 分别返回 `breach`、`unknown`、`within_limit`，并解释第一行1500已超过1000，先返回breach，不再继续判断完整性。本轮在给定骨架和规则后的分支及等号边界判断通过；脱离提示重写函数和完整源码讲解仍可后续验收。
